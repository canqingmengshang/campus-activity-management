## 2. WBS分解思路
本次WBS分解严格遵循**成果导向、三级结构、可分配、可验收**四大原则，不出现任何动作类描述，全部以可交付成果为最小单元。
一级按项目管理领域划分为项目管理成果、需求范围成果、计划编制成果、配置管理成果、协作与总结成果五大模块；
二级按阶段与模块拆分，确保独立性与完整性；
三级细化到可直接分配工期、责任人、纳入进度计划的最小交付物，结构清晰、层次分明、逻辑严谨。
分解过程反复校验、多次优化，确保每个交付物都对应明确价值、无冗余、无遗漏、可追溯、可评分。

## 3. 进度安排依据
进度计划严格基于WBS三级交付物进行活动拆解，确保每个活动都对应明确的可交付成果，做到“活动源于成果、成果支撑目标”。
依据实验时长，合理分配各阶段工期，兼顾任务难度、依赖关系与协作成本，避免工期过紧或资源浪费。
进度安排明确前置、并行、后续逻辑，关键路径清晰、里程碑明确、责任分工到人。
同时预留缓冲时间，用于文档修改、冲突处理、版本回退与内容优化，保证实验质量与进度可控。整体进度计划逻辑严谨、安排合理、可执行性强，满足课程实验要求。

## 4. 配置管理与协作过程
作为配置管理员，我全面负责配置项识别、目录规划、分支策略设计、命名规范制定、提交规则统一、版本管控、变更跟踪、冲突处理与过程留痕。
首先识别所有配置项，包括文档、目录、脚本、资源、记录等，建立受控清单；
采用main+dev+feature三级分支策略，main为最终稳定版本、dev为开发集成、feature为个人开发分支，严格执行feature→dev→main逐级合并；
统一文档命名、分支命名、提交信息格式，确保规范统一；
全程保留完整提交历史，关键节点打版本标签；
协作过程严格按规范执行，变更有据、版本清晰、过程可审计、成果可追溯，有效保障了项目质量与协作效率。

## 5. 冲突解决过程记录
本次实验重点模拟真实团队协作中的合并冲突。
刘广兴在feature-liuguangxing分支修改docs/conflict.md的结论行，陈文裕在feature-chenwenyu分支修改同一文件同一位置，人为制造内容冲突。
合并到dev分支时，Git无法自动合并，提示冲突并标注冲突范围。刘广兴第一时间识别冲突、定位差异、组织协商，与陈文裕共同分析两种方案的合理性：直接合并到main虽快但风险高；先dev验证再合并main更稳定、更符合项目管理规范。
最终确定采用“先dev验证、后main发布”的稳妥方案，手动删除Git冲突标记，整合形成统一结论，提交并标注冲突解决记录，最终合并到dev并审核合并到main。整个冲突处理过程规范、透明、可追溯，有效提升了团队协作与沟通能力。

文档排版、格式统一、细节校对不够细致。

### 改进方向

严格执行配置管理规范，统一命名、提交、分支规则；
反复练习Git冲突处理流程，提升协商效率与操作熟练度；
制定统一文档模板，强化格式规范与细节校对，提高文档质量；
加强团队沟通，提前对齐需求与标准，减少返工与冲突。
